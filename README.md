# kimi-code-subagent-skill

> 让主智能体只负责分工和汇报、执行全部委派给专业子智能体的 Kimi Code skill。
> 借鉴 [subagent-isolation](https://github.com/Wolido/subagent-isolation)（MIT）的强制隔离思想，适配 Kimi Code 的 Agent 机制。

---

## 一、原理：为什么要这么设计

大语言模型的上下文不是无限的。当一个智能体同时负责读代码、改代码、跑测试时，工具调用痕迹、报错信息、中间结果会迅速堆积；超过模型能稳定处理的阈值后，推理质量明显下降——关键信息被淹没、重复劳动增多、决策开始基于嘈杂的上下文。

本 skill 的核心模式：**把任务切成小块，按块选专业角色，派给分工明确的子智能体**。每个子智能体在干净上下文里执行，只拿到委派的那一段说明（含角色定义）；主智能体只保留"要做什么"和"结果是什么"，负责拆分、选角、委派、汇总、汇报。

对应地，要避免的分工混乱根源有六类：

| 问题 | 后果 | 对策 |
|------|------|------|
| 主智能体忍不住自己动手 | 上下文被工具痕迹污染，推理质量下降 | 执行类工作一律委派，主智能体绝不编辑/跑命令 |
| 任务不拆分，一个智能体全干 | 上下文膨胀，关键信息被淹没 | 拆成可独立验证的任务，逐个委派 |
| 子智能体职责不清、角色混用 | 重复劳动、改同一文件互相覆盖 | 从角色库选角，每个子智能体只演一个角色 |
| 委派任务含糊 | 子智能体自由发挥，结果不符合预期 | 用标准任务格式：背景/输入/要求/输出格式/验收标准 |
| 并发乱用 | 同文件被多个子智能体同时改，冲突 | 独立任务才并行；有依赖或同文件的串行 |
| 递归无边界 | 子智能体再派子智能体，范围失控 | 只有主智能体能委派；子智能体不继续下派 |

## 二、设计思想

Kimi Code 底层子智能体只有三种类型（`explore` / `plan` / `coder`），但**角色靠委派 prompt 注入**：派活时把对应角色的定义（职责、边界、流程、输出格式、约束）写进 prompt 开头，子智能体就被"塑形"成该专业角色。底层类型决定它能碰什么工具，角色定义决定它怎么做、怎么交。

四个层面的隔离：

- **上下文隔离** — 子智能体看不到主智能体的执行痕迹，只拿到委派的那一段说明
- **能力隔离** — 通过底层类型和可携带技能，精确控制每个角色能做什么、不能做什么
- **职责隔离** — 每个子智能体只演一个角色，只做派给的那一件事
- **递归边界** — 只有主智能体能委派，子智能体不得继续下派，任务范围始终可控

## 三、角色分工

| 角色 | 底层类型 | 职责 | 可携带技能 | 硬性约束 |
|------|---------|------|-----------|---------|
| **调研员** investigator | `explore` | 摸清现状：定位文件、读懂逻辑、找出根因线索 | `improve-codebase-architecture`（架构深化分析） | 只读，不改任何文件 |
| **规划师** planner | `plan` | 出实施方案：拆步骤、比较方案、预估风险 | `grill-me`（拷问方案）、`to-spec`（产出规格）、`to-tickets`（拆 tickets） | 只读，不实现 |
| **编码员** coder | `coder` | 写代码、改代码、跑验证 | `tdd`（测试先行）、`implement`（按 spec/tickets 实现，含测试闭环） | 不做全局规划，只做派给的那件事 |
| **测试员** tester | `coder` | 写测试、补覆盖、跑测试并报结果 | `tdd`（红绿循环纪律） | 不顺手改业务逻辑 |
| **评审员** reviewer | `explore` 或 `plan` | 只读评审：正确性/清晰度/可维护性/一致性 | — | 绝不修改文件 |
| **文档员** writer | `coder` | 写文档、README、注释、commit message、PR 描述 | — | 不实现逻辑，只写内容 |
| **调试员** debugger | `coder` | 修 bug：先找根因，再最小修复，验证后收尾 | — | 不允许"试错式"乱改 |

每个角色委派时都注入同一套角色定义模板（职责边界 / 可用技能 / 工作流程 / 输出格式 / 约束），并以固定标记结尾汇报，例如编码员 `[coder: done]`、评审员 `[reviewer: done]`。主智能体收到标记即知任务完成。

### 角色可调用工具（工具白名单）

底层类型决定工具上限（`explore`/`plan` 天然没有写工具，`coder` 全量），角色纪律决定怎么用。委派时把对应角色的工具边界一并写进 prompt：

| 角色 | 允许调用 | 明确禁止 | 说明 |
|------|---------|---------|------|
| **调研员** | `Read`、`Glob`、`Grep`、`Bash`（仅只读命令）、`WebSearch`、`FetchURL` | `Write`、`Edit` | 只读探索，摸清现状 |
| **规划师** | `Read`、`Glob`、`Grep`、`WebSearch`、`FetchURL` | `Write`、`Edit`、`Bash` | 纯只读规划，不跑命令 |
| **编码员** | `Read`、`Write`、`Edit`、`Grep`、`Glob`、`Bash`、`Skill`、`TodoList`、`TaskList`、`WebSearch`、`FetchURL` | 纪律禁止：不碰任务外文件 | 唯一能改文件/跑命令的角色 |
| **测试员** | 同编码员 | 纪律禁止：不顺手改业务逻辑 | 写测试、补覆盖、跑验证 |
| **评审员** | `Read`、`Glob`、`Grep`、`Bash`（仅只读命令） | `Write`、`Edit` | 只读评审，绝不改文件 |
| **文档员** | `Read`、`Write`、`Edit`、`Grep`、`Glob`、`Skill` | 纪律禁止：不实现逻辑 | 只写文档类内容 |
| **调试员** | 同编码员 | 纪律禁止：试错式乱改 | 先找根因再最小修复 |

### 可调用技能（能力库）

角色除了底层类型，还能携带技能——委派时在 prompt 里注明"加载 XXX 技能"，子智能体即可用对应能力干活（用 `Skill` 工具加载）。

| 技能 | 挂载角色 | 什么时候用 | 怎么触发 |
|------|---------|-----------|---------|
| `grill-me` | 规划师（及主智能体拆任务前） | 方案出炉后先自我拷问：边界、假设、反例、遗漏场景；主智能体也可在拆任务前用它向用户质询需求 | 委派 prompt 写明"用 grill-me 拷问你的方案" |
| `to-spec` | 规划师 | 需求已讨论清楚，需要把它综合成 spec/PRD 发布到 issue tracker | 委派 prompt 写明"用 to-spec 产出 spec" |
| `to-tickets` | 规划师、主智能体 | 有方案/spec 后，拆成 tracer-bullet vertical slices，声明 ticket 阻塞关系 | 委派 prompt 写明"用 to-tickets 拆 tickets" |
| `tdd` | 编码员、测试员 | 任何"写代码/写测试"任务，默认都应走红→绿循环，测试先行 | 委派 prompt 写明"按 tdd 纪律实施" |
| `implement` | 编码员 | 按 spec/tickets 实现完整工作：用 tdd 写测试、常跑类型检查/单测、最后跑全量测试套件，完成后交给评审 | 委派 prompt 写明"用 implement 流程执行" |
| `improve-codebase-architecture` | 调研员 | 要扫描架构找深化机会（深模块/浅模块、seam、adapter），产出报告 | 委派 prompt 写明"用 improve-codebase-architecture 扫描并出报告" |

> **注意**：`to-spec`、`to-tickets` 依赖项目的 issue tracker（`docs/agents/issue-tracker.md`）。若项目没有，先跑 `/setup-matt-pocock-skills` 建立，否则这两个技能无法发布/拆单。

## 四、工作流程

1. **拆任务** — 把需求拆成可独立验证的块（单一职责、明确边界、可验收）
2. **选角** — 每块从角色库选一个角色
3. **委派** — 用五段式格式 + 角色定义派出去
4. **等回传** — 收到全部结果前不决策
5. **汇报** — 汇总给用户：谁干了什么、验证是否通过、遗留问题

### 委派任务格式（五段式，必须写全）

```
### 背景
任务来源、已完成上下文、为什么做这个

### 输入
相关文件路径、数据、已有结论

### 要求
明确的任务清单，可逐项检查；划清边界（哪些文件不许碰）

### 输出格式
期望返回的结构（按所选角色的输出格式）

### 验收标准
- [ ] 具体检查项（含验证命令）
```

### 并行 vs 串行

- **并行**：多个任务互不依赖、不碰同一批文件 → 同一消息里发多个 `Agent` 调用（或同角色多输入用 `AgentSwarm`）
- **串行**：后一个任务依赖前一个的结果（如流水线）→ 等前一个回传后再派
- **禁止**：多个子智能体并发改同一个文件

## 五、子智能体如何向用户提问

子智能体看不到用户，只能回传结果给主智能体。需要用户回答时：

- **该问**：影响任务方向、范围、验收标准、方案取舍的问题（如 tdd 的测试 seams、to-spec 的发布目标）
- **不该问**：小歧义、能从代码/上下文推断的事——自己做合理假设并继续，最后在报告里标注"我假设了 X"

必须问时，输出标准块并停止，不得臆造：

```
<question>
- 问题：<一句话问题>
- 背景：<为什么需要回答、影响哪个决策>
- 选项（可选）：A. ... / B. ... / C. ...
- 影响：<不回答会怎样>
</question>
```

主智能体收到后：能自己答就不打扰用户；不能确定则转述给用户（并行场景合并问题一次性问）；用户回答后通过 `resume` 恢复对应子智能体、把答案注入继续执行。

## 六、安装与使用

**安装**：把 `SKILL.md` 复制到 `~/.kimi-code/skills/subagent/`（Windows 用户路径：`C:/Users/HP/.kimi-code/skills/subagent/`），重启 Kimi Code 即可识别。

**使用**：在 Kimi Code 中输入 `/subagent <任务描述>` 激活。

**何时不用**：小改动（一两行、单文件小修）直接做别拆；纯对话问答不需要执行；用户明确要求主智能体自己动手的场景。
